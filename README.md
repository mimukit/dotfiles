# Dotfiles

A repository with my personal configuration files, powered by [chezmoi](https://github.com/twpayne/chezmoi)

## How to use

- Install `chezmoi` following [this guideline](https://www.chezmoi.io/install/)

- Initialize chezmoi with your dotfiles repo:

```
chezmoi init https://github.com/mimukit/dotfiles.git
```

- Check what changes that chezmoi will make to your home directory by running:

```
chezmoi diff
```

- If you are happy with the changes that chezmoi will make from remote then run:

```
chezmoi -v apply
```

- If you want to update chezmoi remote with current local changes, then run:

```
chezmoi add $FILE
```

- Some tools (Topgrade, AI-skill installers, Neovim plugin managers, app
  auto-updaters) edit files in `$HOME` directly without going through
  `chezmoi edit`, so those changes never reach the chezmoi source. To pull them
  back in, run the sync script (or the `czs` alias). It re-adds modified files,
  adds new ones in the listed dirs, and (after confirmation) prunes source
  entries that were deleted from the target. Edit the path lists at the top of
  the script to control what gets synced:

```
~/.local/bin/chezmoi_sync.sh            # sync listed paths into the source
~/.local/bin/chezmoi_sync.sh --dry-run  # preview what would change
```

Two files are deliberately missing from that script's re-add list, and both would look covered while doing nothing. `~/.claude/settings.json` and `~/.codex/config.toml` are managed by `modify_` scripts, which `chezmoi re-add` skips; the extract steps in the same script handle them. `~/.gitconfig` is a template now, and `re-add` skips a template just as silently. Edit `private_dot_gitconfig.tmpl` and apply.

## Orca

Orca keeps its preferences in one blob it rewrites every few seconds, mixed in
with state that belongs to whichever machine is running:

```
~/Library/Application Support/orca/profiles/local-default/orca-data.json
```

That file can't be tracked whole — it would carry another machine's repos,
worktrees, absolute paths and telemetry id across. Instead a curated slice of it
is tracked and merged in on apply:

- `.chezmoitemplates/orca-settings.json` — the tracked keys (151 of ~183
  `settings`, plus 31 genuine `ui` preferences). Generated by
  `~/.local/bin/orca_settings_export.sh`, which is also where the key policy
  lives.
- `private_Library/.../modify_orca-data.json.tmpl` — a chezmoi `modify_` script.
  On apply it receives the live file on stdin, overlays only the tracked keys and
  passes everything else through, so `repos`, `worktreeMeta`, `sshTargets`,
  window geometry and `telemetry.installId` stay local.
- `dot_orca/keybindings.json` — tracked as a plain file.

Deliberately **not** tracked: `~/.orca/agent-hooks/` (Orca reinstalls those on
every upgrade), and the rest of the app-support dir — sqlite DBs, cookies,
caches, terminal history, device-pairing tokens, e2ee key material. Machine
identity, managed agent accounts and proxy/mobile settings are withheld from the
tracked slice too. No OAuth tokens live in the settings blob.

**Quit Orca before `chezmoi apply`.** A running Orca holds this state in memory
and will overwrite the file on its next save. Order: quit → `cza` → relaunch.
On a new machine: install Orca, launch once, quit, then apply.

`chezmoi diff` is not readable here — Orca writes the blob on a single line, so
any change shows as a 109 KB rewrite. To see what an apply would actually do:

```
ORCA=~/"Library/Application Support/orca/profiles/local-default/orca-data.json"
diff <(jq -S . "$ORCA") <(chezmoi cat "$ORCA" | jq -S .)
```

## Claude Code

`~/.claude/settings.json` has three writers. We own the top-level keys and three
hook entries calling `~/.local/bin/agent-hook`. Orca adds twelve entries calling
`~/.orca/agent-hooks/claude-hook.sh`, and herdr adds a SessionStart entry. Both
reinstall on launch and rewrite their command string on upgrade, so tracking the
file whole meant a diff in the source after every vendor build.

Turning Orca's hooks off is not the fix. Its "Agent status hooks" setting gates
the hook server, not just the install: with it off, Orca opens no port and strips
`ORCA_AGENT_HOOK_PORT` from every new pane, so a hand-installed relay posts to
nothing and the working/waiting/done pane indicators are gone for good.

So the file is split, the same way Orca's blob is:

- `.chezmoitemplates/claude-settings.json` — our keys. Generated by
  `~/.local/bin/claude_settings_export.sh`, which is also where the ownership
  rule lives.
- `private_dot_claude/modify_settings.json.tmpl` — a chezmoi `modify_` script. On
  apply it receives the live file on stdin, merges our keys in, and leaves every
  vendor hook entry where it found it.

The source directory carries the `private_` prefix because Claude Code chmods
`~/.claude` to `0700` on launch. chezmoi's default for a directory is `0755`, so
every `chezmoi apply` found a mode it had not written and stopped to ask ".claude
has changed since chezmoi last wrote it?". The prefix makes chezmoi target `0700`
too, and the two writers agree.

The two are exact inverses, so export → apply is a no-op. Drift flows back on
`czs`: a permission you approved with "don't ask again", or a theme or model set
in the app, lands in the source on the next sync.

Edit `.chezmoitemplates/claude-settings.json`, never the target. And never run
`chezmoi add ~/.claude/settings.json` — unlike `re-add`, which skips `modify_`
entries, `add` deletes the script and puts a plain file in its place.

## Codex

`~/.codex/config.toml` is the third file with this shape. Codex keeps the
preferences you tune next to state that belongs to one machine and one build of
ChatGPT.app:

| withheld | what it is |
| --- | --- |
| `notify` | absolute path into the ChatGPT.app bundle |
| `marketplaces` | `last_updated` stamps and `~/.cache` paths |
| `projects` | a trust decision per absolute directory, and a readable index of every project on the machine |
| `mcp_servers` | vendor-installed, pins an app build number |
| `shell_environment_policy` | vendor build hashes |
| `hooks.state` | a `trusted_hash` per hook, rewritten whenever `hooks.json` changes |
| `tui.model_availability_nux` | first-run counters |

Codex rewrites its share whenever you trust a directory or take an app upgrade,
so tracking the file whole put a diff in the source after every session. It is
split the same way:

- `.chezmoitemplates/codex-config.toml` — our keys. Generated by
  `~/.local/bin/codex_settings_export.sh`, which is also where the key policy
  lives. The policy is a deny list, not an allow list, so a preference a future
  Codex build adds is captured on the next sync instead of being dropped.
- `dot_codex/modify_private_config.toml.tmpl` — a chezmoi `modify_` script. On
  apply it receives the live file on stdin, overlays our keys and leaves the rest
  where it found it.

The merge runs on `uv run --with tomlkit`, not `jq`, because the payload is TOML.
tomlkit parses into a style-preserving tree, so key order, quote style and blank
lines survive and an apply that changes nothing returns the same bytes. `dasel`
was tried first and rejected: it round-trips without losing data, but
alphabetises every table and rewrites double quotes as single, which would
rewrite the file on every apply and never let `chezmoi status` settle.

Same two rules as Claude Code: edit `.chezmoitemplates/codex-config.toml`, never
the target, and never run `chezmoi add ~/.codex/config.toml`.

## Externals and machine-local files

`.chezmoiexternal.toml` clones zinit and tpm, so a new machine needs no manual
clone step. `.zshrc` no longer clones zinit itself. The yazi flavors stay out of
it on purpose: `ya pkg` owns those files and pins them in
`.config/yazi/package.toml`, which chezmoi does track. Restore them with
`ya pkg install`.

One consequence: `chezmoi verify` now exits 1 even when nothing is pending,
because it cannot compute the state of a `git-repo` external without a network
fetch. `chezmoi diff`, `chezmoi status` and `chezmoi apply --dry-run` are all
accurate. Use `chezmoi verify --exclude=externals` when you want an exit code to
mean something.

`~/.gitconfig.local` is included from the end of `~/.gitconfig` and is not
tracked. It holds keys a tool generates per install, starting with
`coderabbit.machineId`. Note that `git config --global` always writes to
`~/.gitconfig`, never to an include, so a regenerated key lands in the tracked
file and the next `czs` offers it back. Reject it in the diff and move the value
across.

- If you are not happy with the changes to a file then either edit it with:

```
chezmoi edit $FILE
```

- Or, invoke a merge tool (`nvim -d`, set in `.chezmoi.toml.tmpl`) to merge changes between the current contents of the file, the file in your working copy, and the computed contents of the file:

```
chezmoi merge $FILE
```

- On any machine, you can pull and apply the latest changes from your repo with:

```
chezmoi update -v
```
